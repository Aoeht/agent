# 大模型部署框架知识文档

> vLLM / SGLang / TensorRT-LLM / LMDeploy 等 · 面向使用者 · 2026-10-19
> 本机环境锚点:单卡 RTX A5000(24G, sm86, 驱动 565)、vLLM 0.18.1、SGLang 0.5.16、部署脚本 `~/deploy_model/serve_qwen35_4b.sh`

---

## 0. 部署框架解决什么问题

最朴素的推理方式是用 transformers 写循环:模型每次生成一个词,循环调用。这样做有三个致命问题:

1. **Python 开销占比巨大**:GPU 算一个 token 只要几毫秒,但 Python 调度、kernel 启动、采样逻辑可能要十几毫秒——GPU 大部分时间在空转。
2. **KV Cache 反复重算**:朴素实现里每生成一个 token,要么重算全部历史,要么自己手工管理缓存。
3. **无法并发**:一个请求独占整卡,第二个请求只能干等。

部署框架(vLLM、SGLang 等)就是把这三件事系统化解决的基础设施。**它们不改变模型本身,只是让同样的 GPU 产出更多 token、更快地返回第一个字。**

### 先建立两个核心指标

| 指标 | 含义 | 谁关心 |
|---|---|---|
| **TTFT**(Time To First Token) | 发出请求到收到第一个字的时间 | 聊天/Agent 的"手感" |
| **TPOT / ITL**(每 token 生成时间) | 之后每个字之间的间隔,倒数即"单流速度" | 打字机体验;你的 29.6 tok/s 就是它 |

还有吞吐(throughput, tok/s 全系统)和 goodput(满足延迟约束下的有效吞吐)。**延迟和吞吐天然互斥**,所有参数调优都是在两者之间找你要的平衡点。

## 1. 一切优化的出发点:Prefill 和 Decode 是两个不同的活

LLM 推理分两个阶段,**瓶颈性质完全不同**,框架的所有技术都由此展开:

```
Prefill(预填充): 一次吃进整个 prompt,并行算出所有 token 的 KV
                 → 计算密集型,GPU 利用率高,快
Decode(解码):   逐 token 生成,每步只算一个 token
                 → 访存密集型(要把全部权重和 KV 从显存搬一遍才算一步)
                 → GPU 算力大量闲置,速度上限 = 显存带宽 ÷ 模型大小
```

**Decode 阶段慢的本质是"搬运"而不是"计算"**——这就是为什么:
- 你的 A5000(768 GB/s 带宽)单流解码上限 ≈ 8.45GB 权重 × (1+少量开销) ÷ 768GB/s ≈ 30+ tok/s,你实测 29.6 tok/s,**已经贴着硬件天花板**;
- 并发 decode(一个 batch 里塞多个请求)几乎不增加时间成本——反正权重都要搬一遍,顺便算 8 个请求和算 1 个差不多快。**高并发是部署框架最大的价值来源**。

## 2. KV Cache:显存账本(必须会算)

Attention 生成时,每个 token 的 Key/Value 要留作后续 attention 的依据,这就是 KV Cache。

**公式**(只对 GQA 模型):

```
KV 显存 = 2(K和V) × 层数 × KV头数 × 头维度 × 序列长度 × 每元素字节数
```

以 Qwen3.5-4B 这类小模型(层数少、KV 头数少,典型的 4B 级配置约 36 层 × 4 个 KV 头 × 128 维,bf16)算,**单条 4096 token 序列的 KV 约 0.9~1.2GB**——和权重(8.45GB)同量级,不是小钱。

由此推出几个实用结论:

- `--max-model-len` 每翻一倍,KV 预算翻倍。给 4096 够用就别开 32768;
- 并发 N 条请求 = N 份 KV。24G 卡上"权重 8.45G + 剩余给 KV",决定了你最多同时服务多少请求、每条多长;
- **上下文长度是商品,显存是货币**。所有框架的显存参数(下文)本质上都在分配这笔预算。

## 3. 核心技术逐个讲(每个都按"怎么出现 → 解决什么"展开)

### 3.1 Continuous Batching(连续批处理)—— 并发调度的基石

**怎么出现的**:2022 年 Orca 论文(OSDI'22)之前,推理服务用"静态 batching":攒一批请求一起算,等最长的那个生成完才整批返回——短请求陪着长请求干耗,GPU 利用率很差。Orca 提出**迭代级调度**:每生成一步都重新组队,谁完成了立刻让新请求顶上。

**解决什么**:吞吐量从"整批等最慢请求"的假并发变成真并发,通常带来数倍到数十倍吞吐提升。今天所有框架的默认行为。
==🟠**批注：**实现真并发，让一批里完成的请求立刻让后面排队的上==
### 3.2 PagedAttention(vLLM, 2023)—— KV Cache 的"虚拟内存"

**怎么出现的**:vLLM 团队(UC Berkeley, SOSP 2023 论文)发现 KV Cache 的经典存法是按请求连续分配一大块显存,但没人知道请求会生成多长,只能按"最大可能长度"预留 → 平均浪费 60-80%。他们借鉴操作系统**虚拟内存分页**:把 KV 切成固定大小的 block(如 16 token/块),按需分配、逻辑连续物理离散,用页表映射。

**解决什么**:
- 显存浪费从 60-80% 降到 4% 以下 → 同卡并发容量翻几倍;
- 相同前缀的请求可以共享物理 block(这演变成后来的 prefix caching);
- 也让"显存不够时把某些请求换出/重算"成为可能(preemption)。

这是 vLLM 的立身之本,也是"vLLM"名字的来源(Virtual LLM)。
**==🟠批注：解决显存分配策略太保守的问题，用虚拟内存的思路分配显存==**
### 3.3 RadixAttention / Prefix Caching(SGLang, 2024)—— 让"重复的开头"免费

**怎么出现的**:SGLang 团队(LMSYS,NSDI 2024 论文)观察到大量真实负载里前缀高度重复:多轮对话的历史、同一个 system prompt、Agent 的工具定义、few-shot 示例……这些每条请求都在重算,纯浪费。他们用**基数树(radix tree)管理 KV Cache**:前缀相同 → 直接复用树的枝干,只算新增部分。

vLLM 后来也实现了自己的版本(block-hash 前缀缓存),目前能力接近。

**解决什么**:多轮对话第二轮的 TTFT 可以从秒级降到几十毫秒;Agent 类反复携带长 system prompt 的场景总吞吐成倍提升。**前缀命中率越高的负载,SGLang 相对优势越大**——这是它最核心的卖点。
**==🟠批注：解决prompt开头、system prompt、结构化输入的相同token每次要重新计算==**
### 3.4 CUDA Graph —— 你的 8.3 → 29.6 tok/s 之谜

**怎么出现的**:Decode 每步要启动成百上千个小 CUDA kernel,每个 kernel 启动有 ~10μs 级 CPU 开销,累加起来 CPU 反而成了瓶颈(NVIDIA 官方数据显示传统模式下 CPU 开销可占单步延迟一半以上)。CUDA Graph 是 NVIDIA 提供的机制:**把一整套 kernel 调用录制成一个"图",之后每次只发一条指令回放**。

**解决什么**:消灭逐 kernel 的启动开销。**你自己的实测就是最好的证据:同一模型 eager 模式 8.3 tok/s,开 CUDA Graph 29.6 tok/s,差 3.6 倍**。

细节:
- 图是按 batch size 预先录制的(vLLM 的 `cuda_graph_bs` 列表,默认 [1,2,4,8,…]),实际 batch 不在列表里就 pad 到最近的档位;
- 所以 `max_num_seqs` 设多大,图就录多大,显存也多占(你的脚本 `max-num-seqs=1`,只录 bs=1 的图,省显存);
- 这就是为什么 vLLM 旧脚本里的 `--enforce-eager` 是性能杀手——你已经在脚本里去掉它了。
**==🟠批注：解决decode时需要逐个token的计算，cuda graph直接按batch size搞成一个图==**
### 3.5 Chunked Prefill —— 长 prompt 不阻塞别人

**怎么出现的**:连续批处理后仍有一个调度难题:一条 32K token 的长 prompt 送进来,prefill 要独占 GPU 好几秒,期间所有正在 decode 的请求全部卡顿(TTFT 好但 ITL 突刺)。

**解决什么**:把长 prefill 切成小块(如 2048/块),每步只算一块,和 decode 混合调度。长请求的 TTFT 略增,但全系统延迟平稳。vLLM 的 `max-num-batched-tokens`、SGLang 的 `chunked-prefill-size` 就是这个块的尺寸。你现在 `max-num-seqs=1` 用不到,上并发时是必开项。
**==🟠批注：解决prefill和decode的显存竞争占用，直接把prefill的prompt切块和decode的请求一起算==**
### 3.6 Speculative Decoding(投机解码)—— 用"猜测-验证"绕过访存瓶颈

**怎么出现的**:Decode 慢是因为每步都要搬全部权重。2023 年起出现一族方法:用便宜的东西(小模型、n-gram、模型自带的 MTP 小头)先猜出 k 个 token,**大模型一次前向并行验证**——猜对了等于一步生成 k 个 token,搬运成本不变。

**解决什么**:单流速度 1.5-3 倍。关键在**接受率**:模型行为越好猜越赚;拒答率高反而变慢(验证也花钱)。

**你环境的注脚**:Qwen3.5 的权重里有 `mtp.*` 辅助头(多 token 预测),就是给投机解码用的——你合并 LoRA 时的输出刻意不含它,所以当前部署用不上;哪追求极致单流速度,可以带着 MTP 头重新合并,让 vLLM 开投机解码。
==🟠**批注：解决decode每次要重新搬运token到显存上的瓶颈，让小模型先猜出k个token，大模型再验证**==
### 3.7 结构化输出(Constrained Decoding)—— 你验证过的 JSON 方案

**怎么出现的**:应用要求模型输出严格合法的 JSON/SQL/枚举,靠 prompt 恳求不可靠。2023-2024 年出现 grammar 约束解码:把 JSON Schema 编译成**逐 token 的允许/禁止掩码**,每步采样前把不合法的 token 概率清零。

**解决什么**:100% 合规输出。代表实现 **xgrammar**(2024):把 schema 编译成 EBNF 再预编译成 token 位掩码,比早期 outlines/guidance 快一个量级。vLLM 和 SGLang 都集成了它。

**实践注脚(你实测过的)**:第一个请求会包含 grammar 编译开销(秒级),之后复用缓存;`response_format={"type":"json_schema",...}` 即 OpenAI 兼容写法。你的测试脚本 `~/deploy_model/test_sglang_json.py` 是通用的,传 BASE_URL 可测任何框架。

### 3.8 服务化量化 —— GPTQ / AWQ / FP8

权重压到低比特,KV 也能压(kv_cache_dtype)。选型速查:

| 方案                     | 比特  | 精度损失 | 你的 A5000(sm86)能用吗       |
| ---------------------- | --- | ---- | ----------------------- |
| GPTQ / AWQ(INT4)       | 4   | 小    | ✅ 框架成熟,权重体积 ÷4          |
| SmoothQuant/W8A8(INT8) | 8   | 很小   | ✅                       |
| FP8(E4M3)              | 8   | 极小   | ❌ 需 sm89(Ada)以上,你是 sm86 |

4B 模型只有 8.45G,暂不需要量化;哪天换 30B+ 的模型,AWQ/GPTQ 是 24G 卡的常规操作。

### 3.9 并行策略(单卡用不到,概念要知道)

- **TP(张量并行)**:把每层权重矩阵切开,多卡各算一块,每层间通信一次。最常用,延迟友好,但要求卡间高速互联(NVLink);
- **PP(流水线并行)**:按层切,卡间传激活,通信少但有空泡;
- **EP(专家并行)**:MoE 模型的专家分散到各卡;
- **DP(数据并行/注意力 DP)**:复制整个模型跑不同请求,配合前缀缓存做超大集群。
- 单卡 24G 的世界里:**这些都不用管**,到多卡机再学。

### 3.10 其他值得知道的机制(一句话版)

- **Overlap Scheduler**:调度器在 GPU 算第 N 步时同步准备第 N+1 步的输入,藏起 CPU 开销(SGLang 的 zero-overhead 调度器、vLLM 的 async scheduling 都是这事);
- **Preemption**:显存不够时把优先级低的请求 KV 换出(swap 到 CPU)或直接丢弃重算(recompute),保证高优先请求推进;
- **OpenAI 兼容 API**:所有主流框架都提供 `/v1/chat/completions` 兼容层,换框架 = 换 base_url,代码不用改。

## 4. 主流框架逐个看

### 4.1 vLLM ⭐ 你的现役框架

- **出身**:2023.6 UC Berkeley 开源,学术出身(SOSP'23 最佳论文级),2023-2024 爆发式成为社区默认;2025 年初重写了引擎(V1 架构)。
- **核心招式**:PagedAttention + Continuous Batching,后来补齐 prefix caching、chunked prefill、spec decode、xgrammar。
- **优势**:
  - **生态第一**:模型支持最广最快(新架构往往数天内有支持)、文档/社区/工具链最全、OpenAI 兼容层最标准;
  - 生产验证量大,坑被踩得最干净;
  - 多模态、LoRA 多租户(`--enable-lora`)、量化方案支持齐全。
- **劣势**:历史包袱多(默认参数偏保守);极端高并发和前缀重负载下吞吐常被 SGLang 压过一头;对最新硬件的极限优化不如 NVIDIA 自家栈。
- **适合你**:✅ 模型支持稳、JSON 输出已验证、单卡场景成熟度最高——你的默认选择。

### 4.2 SGLang ⭐ 你试过并暂时搁置的

- **出身**:2024.1 LMSYS 开源,起点是 RadixAttention 论文(NSDI'24),名字来自其结构化编程语言(SGLang 前端)。
- **核心招式**:RadixAttention 前缀缓存 + zero-overhead scheduler + FlashInfer 内核深度集成;2025 年起是 DeepSeek 系 MLA 架构优化的主战场(DP attention 等)。
- **优势**:
  - **多轮/Agent/高前缀复用场景的延迟和吞吐常居第一**;
  - 内核激进,JIT/编译内核迭代快;
  - 大并发吞吐榜(Prefix 级 benchmark)常客。
- **劣势**:
  - **版本节奏激进,兼容性波动大**——你亲身踩过:0.5.16 转向 CUDA 13 优先,对老驱动/sm86 非常不友好(JIT 内核故障+官方 cu129 轮子退役);
  - 生态和文档薄于 vLLM;
  - 优化重心在 H100/B200 级硬件,消费级/专业卡是二等公民。
- **适合你**:等你的驱动升到 580+ 后值得重试(用官方 cu13 栈);或者重负载多轮对话场景再评估。

### 4.3 TensorRT-LLM(NVIDIA)

- **出身**:2023.10,英伟达官方推理库。
- **招式**:把模型"编译"成针对具体 GPU 的定制引擎(kernel 融合、量化、attention 优化做到极致)。
- **优势**:NVIDIA 卡上的性能天花板,企业生产级稳定。
- **劣势**:编译工作流重,模型支持滞后社区数周,灵活性差,调试黑盒。**个人/小团队一般不碰**,除非性能榨取价值极大。

### 4.4 LMDeploy(上海AI Lab/InternLM 团队)

- **出身**:2023,伴随 InternLM 系列推出,TurboMind 引擎。
- **优势**:W4A16/AWQ 量化推理强、吞吐榜常和 SGLang 打平、中文社区文档好。
- **劣势**:国际生态小;模型支持以国产/主流架构为主。
- 适合:量化部署优先、InternLM/Qwen 系用户。

### 4.5 llama.cpp / Ollama

- **出身**:2023.3 Georgi Gerganov 个人项目,C/C++ 实现一切;Ollama(2023.7)在它之上做了易用性封装。
- **优势**:CPU/Mac/边缘设备之王,GGUF 格式一统边缘侧;零依赖、笔记本可跑。
- **劣势**:GPU 服务器高并发场景效率远低于 vLLM/SGLang(无真正的 continuous batching 规模、kernel 优化深度不够)。
- 适合:桌面 Demo、本地玩模型、树莓派;不适合你的生产部署。

### 4.6 TGI(HuggingFace)

- **出身**:2022-2023 年曾经的事实标准(text-generation-inference)。
- 现状:**已明显衰落**,2024 年后社区重心全面转向 vLLM/SGLang,新项目不建议选。

## 5. vLLM vs SGLang 深度对比(2026 现状)

两者技术栈已经高度趋同(都有 continuous batching、prefix caching、chunked prefill、xgrammar、spec decode),差异集中在**基因和优化侧重**:

**哲学差异**

- vLLM 从**显存管理**出发(PagedAttention),先把"浪费的显存"变战斗力,再逐步补全调度优化;工程文化偏稳,默认参数保守。
- SGLang 从**缓存复用**出发(RadixAttention),赌的是"真实负载前缀高度重复";调度器激进重写(zero-overhead),内核 JIT 化,追求每一微秒。

**2026 年公开基准的共识**(各家测起来互有胜负,结论高度依赖负载):

- 高并发大吞吐:互有胜负——有的 H100 实测 vLLM 领先(Jarvis Labs 2026.5),有的 SGLang/LMDeploy 领先(PremAI 2026.2);**前缀命中率是最大变量**;
- 交互式低延迟/Agent 多轮:SGLang 的 RadixAttention 通常赢;
- 生态/易部署:vLLM 公认更强(Red Hat 2026.10 的选型文章结论一致)。

**对你这台机器的落地判断**:

1. 你是**单流低并发 + JSON 结构化输出**场景——前缀复用收益小,瓶颈在单流 decode 上限,而你已经贴到 29.6 tok/s ≈ 显存带宽天花板。**换框架不会更快**;
2. vLLM 在你的硬件(A5000/驱动 565)上是官方支持路径,SGLang 0.5.16 需要 CUDA 13 栈,已验证不可用;
3. 什么时候值得重新评估 SGLang:①驱动升到 580+ 之后(用官方 cu13 栈重装);②业务变成多轮对话/Agent,前缀命中率上来之后。

```bash
--served-model-name qwen35-4b-fraud   # API 里的 model 字段名,和磁盘路径解耦
--tokenizer $TOKENIZER_PATH        # 独立 tokenizer 目录(修过的版本)
--chat-template .../chat_template.jinja  # 显式指定模板 → 和微调时严格一致,避免默认模板漂移
--dtype bfloat16            # 合并模型的存储精度,别用 auto 让它猜
--max-model-len 4096        # KV 预算的直接闸门:4096 对你的业务够用,显存可预期
--max-num-seqs 1            # 只服务单请求:CUDA Graph 只录 bs=1,显存占用最小
--gpu-memory-utilization 0.70  # 框架最多占 70%×24G≈16.8G(权重8.45G+KV+图),留余量防 OOM
--reasoning-parser qwen3    # 若模型输出 <think> 思考段,自动拆分 reasoning/content 字段
HF_HUB_OFFLINE=1            # 离线模式:禁止启动时联网查 HF,既快又稳(配合镜像变量)
```

**显存账本实例**(0.70×24G=16.8G 预算):权重 8.45G + KV(4096×1 请求 ≈1G)+ CUDA 图与激活 ≈2-3G + 框架余量 —— 总计 ~12G,实际留有约 4-5G 安全余量,这就是 0.70 比默认 0.90 稳的原因。

**调参时的思考顺序**(而不是乱试):

```
要上并发了 → 先算 KV 账:剩余显存 ÷ 单请求KV = 并发上限
           → 提高 max-num-seqs + gpu-memory-utilization
           → 打开 chunked prefill
           → 观测:TTFT 和 ITL 哪个恶化,分别对应 prefill/decode 资源
嫌单流慢   → 已到带宽天花板,只能上投机解码(MTP)或换小模型
首字慢     → prefix caching(多轮场景) / 缩短 system prompt
```

## 7. 常见坑(多数你已见过或绕过)

1. **启动即 OOM**:`gpu-memory-utilization` 太大、`max-model-len` 太长、CUDA Graph 档位太多,三者都会吃显存,逐个收。
2. **`enforce-eager` 遗留脚本**:性能直接腰斩再腰斩(8.3 vs 29.6),定期检查脚本里有没有这参数。
3. **推理时模板和训练不一致**:输出质量"莫名"下降。启动时用 `--chat-template` 显式锁死(你已做)。
4. **联网卡住**:启动时 HF 连外网超时。服务器上永远 `HF_HUB_OFFLINE=1`(你已做)+ 本地放好 tokenizer。
5. **把吞吐当单流速度看**:benchmark 工具报的 tok/s 多半是全系统吞吐(并发×单流),你的 29.6 是单流,不要拿不同口径的数字直接比。
6. **首请求特别慢**:可能是 grammar 编译(JSON 模式)或 CUDA Graph 录制或缓存预热——第二请求起再测速度。
7. **框架版本焦虑**:部署框架"能跑、性能达标"就该冻结版本,追新没有收益,只有兼容性风险(SGLang cu13 事件就是教训)。
