# 第 1 章 分词与索引层的坑

## 1.1 bigram 的真实成本：索引膨胀

本仓库对每段连续汉字补 bigram（`src/rag/tokenizer.ts:26`）。收益是"切错也能命中"，代价必须算清楚：一段 n 个汉字的连续文本，Segmenter 给出 k 个词，bigram 额外给出 **n−1 个** token。也就是说中文块的 **`df` 表基数和每个块的 `tf` 表长度都会显著膨胀**，而这直接反映在两处开销上：

- **内存**：`Bm25Index` 每个块存一张 `Map<token, 频次>`（`src/rag/bm25.ts:35` 起的构造逻辑），token 越多表越大。
- **打分耗时**：`search()` 是遍历全部条目 × 全部查询词（`src/rag/bm25.ts` 主循环），块数×词数的乘积里，词表膨胀是线性放大器。

**取舍结论**：bigram 在"几千到几万块"这个量级是纯赚的（召回提升明显、耗时还能接受）；到了几十万块，你要么放弃全量遍历改真倒排链，要么放弃 bigram 只留正经分词 + 向量兜底。本仓库当前 117 块，离天花板很远。

## 1.2 `df` 回收：增量索引最容易写错的一行

`remove()` 必须把该块**独占**的 token 的 `df` 减回去，减到 0 要删键（`src/rag/bm25.ts:73`）。写错的方式有两种，都不报错：

- 忘记回收 → `df` 单调虚高 → IDF 单调虚低 → **稀有的判别性词汇逐渐失去话语权**，排序被高频词主导，检索质量缓慢退化，你可能几周后才察觉。
- 回收过头（按 token 出现次数减而不是按"是否出现在该块"减）→ `df` 偏低 → IDF 虚高 → 常见词突然变得权重极大，噪声命中排到前面。

本仓库有专门一条断言守着这件事："remove 后 df/IDF 与直接重建完全一致"（`tests/rag_ranking.test.ts` 的 `testIncrementalIndex`）。**这类"等价性断言"是增量结构唯一可靠的护城河** —— 单测里拿"增量结果 === 全量重建结果"逐字节比对，比任何单点用例都管用。

## 1.3 归一化没做完会怎样

`tokenize()` 开头做 `NFKC` + `toLowerCase()`（`src/rag/tokenizer.ts:15` 附近）。少做任何一步都会制造"看起来一样但 token 不同"的静默漏检：

| 现象 | 后果 |
|---|---|
| 不做 NFKC | 全角 `ＴＡＶＩＬＹ` 与半角分家 |
| 不做大小写 | `"Tavily"` 查不到 `"tavily"` |
| 不清控制字符 | 网页正文里的 `\u0000`、`\u0007` 混进 token（`normalizeText` 在 `src/rag/chunker.ts:11` 处理，保留 `\t\n`） |
| 不做繁简归一 | "詐騙"查不到"诈骗" —— **本仓库目前没做，是真实缺口** |

繁简这条值得单独提：`Intl.Segmenter` 对繁体照样切词，但繁简字形不同 → token 不同 → 完全对不上。通行解法是在归一化阶段做一次 OpenCC 式的繁简转换（映射到简体检索，输出仍显示原文）。本仓库尚未落地，因为当前语料全是简体。

## 1.4 停用词表的边界

停用词表（`src/rag/tokenizer.ts:10`）里中文只有 15 个、英文 17 个 —— 明显偏小。为什么不抄一份 500 词的通用表？

**因为覆盖率阈值会替你惩罚常见词。** 本仓库的 `coverage` 按 IDF 加权（`src/rag/bm25.ts:119`），而"的""the"这类词在语料里无处不在 → `df` 接近 `N` → IDF 自然趋近 0 → 命中它们几乎不加分，未命中它们也几乎不扣覆盖率。**IDF 已经做了停用词该做的活**，硬编码表只是省一点计算量。

但反过来有个陷阱：**别把领域词放进停用词表。** 反诈语料里的"诈骗"、MCP 语料里的"工具"，一旦被当停用词剔掉，恰好会让最关键的查询词失去话语权。任何"通用中文停用词表"都包含这类在你的领域里非常有信息量的词。

# 第 2 章 BM25 的变体与字段加权

## 2.1 三种常见变体，以及它们各自治什么病

| 变体 | 改动 | 治的病 |
|---|---|---|
| **BM25+** | TF 项给一个下界 δ（常取 1） | 长文档里"只出现一次的重要词"被长度归一压得太狠 |
| **BM15 / 多档饱和** | 更平缓的饱和曲线 | 词堆砌文档仍能靠频次上位的问题 |
| **字段加权 BM25** | title / body / tag 各建一套统计再加权求和 | 标题命中远比正文命中有信息量，但混算会稀释 |

本仓库用的是最标准的 BM25（`k1=1.2, b=0.75`，`src/rag/bm25.ts:37`），三个变体都没做。

## 2.2 为什么 title 加权是这里最划算的一项

注意本仓库有 title 这个字段，而且它不是可有可无的元数据：`splitMarkdown()`（`src/rag/ingest.ts:23`）把标题面包屑写进 `title`（例如 `平台规则 / 客服退款诈骗`），`normalizeSource` 之后它落盘在 doc 上。

但**检索时标题并不参与打分** —— `Bm25Index` 收的是 `chunk.text`（`src/tools/rag_search.ts:80-84` 的索引构建段），`title` 只在返回结果时作为展示字段带出。这意味着现在有个真实的召回缺口：用户查"退款"，而某块的正文只在开头写了"本节目介绍处理流程"、真正说明它属于"客服退款诈骗"这一节的信息在**标题**里 —— 标题不在索引里，这条就只能靠正文其他部分撞上。

**两个可行改法（都还没做）**：
1. **建索引时把面包屑拼进块文本**（最省事，`title + "\n" + text` 一起分词），代价是每块都重复出现标题词，会污染 `df`（标题词在几十块里都出现 → IDF 下降，本来是好信号却被压平）。
2. **字段加权**：标题单独一套 `tf/df`，`score = w_title * s_title + s_body`，`w_title` 取 1.5~3。这才是正确的做法，代价是索引结构要分字段。

这条是本项目"改动小、收益明确"的改进首选。

## 2.3 短语与邻近匹配

"客服退款"在文档里以 `客服` 和 `退款` 两个 token 存在，即使都命中，也不能说明它们**挨在一起**。词袋模型的这个缺陷在两个场景特别疼：

- **否定与并列**："非诈骗 客服" 与 "客服 非诈骗" 打分完全相同。
- **专名查询**：查"反电信网络诈骗法"，任何同时出现这些词但不同篇不同段的文档都会拿高分（本仓库的 `coverage` 反而能压一部分，因为它是 IDF 加权的命中率而非邻近性）。

通行解法是加一层**邻近度打分（phrase boost / proximity）**，或者对完全连在一起的短语命中给额外奖励。本仓库没做，且**优先级应该低于字段加权** —— 前者实现复杂度和调参成本都高不少。

**自查问题**
1. 把标题拼进块文本来"实现标题加权"，副作用是什么？
2. 为什么 `coverage` 阈值能顺带缓解一点词袋噪声，但缓解不了邻近性？

# 第 3 章 切块进阶

## 3.1 中文分句正则必然出错

`splitSentences` 用 `(?<=[。！？!?；;\n])|(?<=\.\s)` 断句（`src/rag/chunker.ts:22`）。这是"能用但一定不完美"的典型：

| 输入 | 错误后果 |
|---|---|
| `依据第 3.5 条规定` | `.` + 空格才断，所以数字小数点安全；但 `第3.5条` 后紧跟空格又会误断 |
| `（详见附录 A） 。` | 括号和句号之间有空格 → 断点位置怪异 |
| `他说："退款。"` | 引号内的句号照样断，把一句引用劈成两块 |
| 英文 `Dr. Smith called` | `Dr.` 后是空格 → 误断 |

**为什么可以接受**：这里的分句不是为了语法正确，而是为了**给重叠提供可搬运的边界**（`:42` 起的装箱逻辑，块尾整句回带到下一块）。切错一句的后果只是重叠位置略歪，不影响 token 集合。真正不能容忍的是"按固定字符数硬重叠"，那会制造出双方都不完整的块。

**什么时候必须换掉**：如果你要让每个块是"可独立阅读的一段"（比如给模型做上下文压缩、或做父子块的子块），那就得上真正的句子分割器（中文用 `punc分割 + 引号配对 + 数字保护`，或直接调用分句模型）。

## 3.2 结构化内容会被拦腰截断

这是本仓库一个**明确已知的缺陷**：装箱是跨行进行的，Markdown 表格、编号列表、代码块都会被切开。一个 12 行的处罚标准表，可能前 7 行在块 A、后 5 行在块 B，而表头在 A —— 于是块 B 拿到的是"5 个数字，没有含义"。

`splitMarkdown` 保护了代码块不被误当标题（围栏状态机在 `src/rag/ingest.ts:38` 附近，`FENCE` 定义在 `:11`），但那是**解析层**的保护，不是**切块层**的保护：正文进了 `chunkText` 之后，表格/列表/代码块都是纯文本，一视同仁按字符数装箱。

**通行解法**：切块前先识别"不可分单元"（表格、列表、代码围栏、公式块），把它们当**原子句**处理 —— 允许超预算独占一块，也允许整单元搬运。代价是块长方差变大，某些块会超 `maxChars`。本仓库目前的做法是：超长的**章节**在入库时被 `maxContentChars=8000` 截断并在报告里点名（`src/rag/ingest.ts:262`），这是兜底不是解法 —— 它保护的是存储，不是语义完整性。

## 3.3 父子块（small-to-big）：性价比很高的一招

问题：小块检索准（粒度细），但喂给模型的上下文太少；大块上下文全，但检索不准。

**通行解法是把两者拆开**：用**小块**做检索（子块），命中后返回它所属的**大块**（父块，或前后相邻块拼接）给模型。LangChain 叫 parent document retriever / Small-to-Big，业界也叫 contextual window。

对本仓库来说落地成本很低：块 id 已经是 `${docId前12位}#${序号}`（`src/rag/knowledge_store.ts` 的 `merge()`，`:253` 附近），序号和文档归属都还在，只要检索命中某个 `#3` 就把同文档的 `#2..#4` 一起取出。**唯一要想清楚的是返回体积**：`top_k=3` × 每篇展开 3 块 = 9 块正文进上下文，token 消耗会数倍上涨，需要配一个"展开块数"的上限。

## 3.4 Contextual chunk：用模型给每块补一段上下文

Anthropic 提出的 **Contextual Retrieval**：入库时对每个块，让 LLM 生成一句"这段出自哪份文档、在讲什么"的前缀，拼在块文本前面再去做 embedding / 建索引。它治的是"块脱离上下文后不可解"这个根因（比如"本节目介绍处理流程"这种开头就没了主语的块）。

**为什么本仓库还没做**：它要在入库阶段对每块调一次模型（成本随语料线性、且需要缓存与失败重试），而本仓库当前连向量检索都没有 —— **收益主要体现在向量召回上**，词法侧的收益要小得多。正确顺序是先有评测集（第 11 章），再决定这项投资值不值。

# 第 4 章 阈值与校准

## 4.1 覆盖率在三种查询下会失真

`coverage = 命中查询词的 IDF 之和 / 全部查询词的 IDF 之和`（`src/rag/bm25.ts:119`），默认阈值 0.25（`src/tools/rag_search.ts:62`）。它比固定分数阈值稳得多，但不是无量纲的普适真理：

| 查询形态 | 失真方式 |
|---|---|
| **长查询（一句话当查询）** | 词多 → 分母大 → 单个关键稀词被稀释。"请帮我查一下平台关于冒充客服的退款诈骗处理规则"里，"客服""退款""诈骗"是信号，"帮我查一下""平台关于"是噪声；后者若 IDF 不为 0，就会压低分子占比 |
| **纯专名查询** | 只有一个高 IDF 词，命中 = 1.0、不命中 = 0.0，阈值形同虚设（要么全过要么全不过） |
| **同义/多语查询** | 未命中的词可能只是**字形不同**，不该算"没答上"——这正是覆盖率判死、向量能救的场景 |

**可行的缓解**（都属于第 10 章的查询理解范畴）：查询前先做**关键词抽取/改写**，把长句压成 3~5 个高 IDF 词，再喂给检索。这一步在本项目**尚未实现**，而且它比看上去有用 —— 它同时改善了覆盖率的分子分母和 BM25 的噪声命中。

## 4.2 阈值应该是扫出来的，不是抄来的，也不是拍出来的

入门篇 12.2 的实测数据（同一份 117 块语料：`0.637 / 0.688 / 0.092`）说明阈值只需落在"真相关"和"完全跑题"之间。但这是**人眼挑的**。系统化做法：

1. 有一组 `(查询, 正确块)` 标注（哪怕 20 条）。
2. 对阈值扫一遍（比如 0.05~0.6，步长 0.05），每个阈值算 recall@3 和 precision@3。
3. 选 recall 刚出现拐点的位置 —— 通常曲线是"阈值升到高 recall 不动、过了某点突然跳水"，跳水点前一点就是好阈值。

**这条流程本身依赖第 11 章的评测集**。没有评测集，0.25 就只能是"量出来的经验值"，且换一份语料就得重新量一次 —— 而这个"重新量"现在没有任何机制会提醒你。

## 4.3 每篇两块的多样性约束与它的副作用

`maxChunksPerDoc = 2`（`src/tools/rag_search.ts:63`，实施在 `take()`：`:219` 起）防止一篇长文占满 `top_k`。副作用要知道：**如果正确答案真的散在一篇文档的 4 个连续块里**（典型：步骤类文档、表格被切成多块），多样性约束会让模型只拿到其中 2 块，答案残缺 —— 而且它看起来像"检索成功"。这是第 3.2/3.3 节两个问题的交叉点：切块破坏结构 + 多样性截断补全。父子块能同时缓解两者。

# 第 5 章 增量索引的正确性陷阱

本仓库实测：48 轮"入库 + 检索"、语料 0→240 篇，全量重建 **1297ms** → 增量 **344ms**。三个必修点，缺一个就会出静默错误。

## 5.1 同分必须定序，否则结果随写入历史漂移

`hits.sort((a,b) => b.score - a.score || (a.id < b.id ? -1 : 1))`（`src/rag/bm25.ts:125`）。

为什么必须：增量 `add` 会改变 Map 的插入顺序，而 `Array.sort` 是稳定的 —— 不写 tie-break，"同分的两个块谁在前"就取决于历史写入顺序，于是**同一份最终语料，两个进程检索结果可能不同**（它们的写入历史不同）。本项目的等价性测试（`testIncrementalIndex`）之所以能断言"逐字节一致"，正是靠这条 tie-break。

**这是并发系统里非常常见的一类 bug**：结果不确定性并不来自数据不一致，而来自**遍历顺序**。

## 5.2 revision 与快照必须配套（一个 await 的距离）

`getIndex()` 的写法很讲究（`src/tools/rag_search.ts:74-99`）：

```ts
const docs = await store.list();      // 可能触发 reload → revision 变化
const revision = store.revision;      // ← 必须在 await 之后再取
// 从这里到 indexed = {...} 之间没有任何 await
```

如果反过来先读 `revision` 再 `await list()`：list 内部重载把 revision  bumped，你就可能把"新快照 + 旧 revision 号"缓存下来 → 上层以为索引是最新的，**永久落后一个版本**，直到下一次写入才侥幸自愈。这类"跨 await 边界读两个相关状态"的错误，是异步代码里最难在 review 中看出来的一类。

**纪律**：任何"我读到 version=N 所以数据是 version=N 的"式推理，都要检查中间有没有 await。

## 5.3 分词缓存的失效判据是内容而不是 id

`tokenCache` 用 `chunkId` 做键，但**必须比对文本**才能复用（`src/tools/rag_search.ts:86` 附近的 `cached?.text === text`）。因为块 id 是 `${docId前12位}#${序号}`，**同一序号在文档改版后指向的是不同内容** —— 只用 id 判存在就会拿旧分词服务新内容，检索到的是"上辈子的文档"。

内存也要留意：这个 Map 随语料线性增长（每块一个 token 数组）。当前做法是每次重建时清掉已消失块的条目（`:96`），所以内存上界 = 当前语料的 token 总量，不会无界增长。若语料再大一个数量级，正确的下一步是 LRU 上限而不是全量驻留。

# 第 6 章 存储与并发

## 6.1 锁的三个设计决定，每个都有反面选项

`acquireLock()`（`src/rag/knowledge_store.ts:130`）用 `fs.open(lockPath, "wx")` 抢锁，Windows/Linux 都是原子创建。三个决定：

1. **超龄判定用 `now()` 比 mtime，不用"进程是否存活"**（`LOCK_STALE_MS = 10_000`，`:65`）。查 PID 存活需要平台相关调用（Windows 上没有 POSIX `kill(pid,0)` 的等价物），而"超过 10 秒还没写完"在临界区只有毫秒级的实现里足够保守。**反面风险**：极慢机器上一次合法写入超过 10 秒 → 被别人抢占 → 两边同时写。缓解办法是把落盘做完就立刻更新锁的时间戳（本项目临界区短，暂不需要）。
2. **等不到锁直接抛错，绝不无锁回落**（`lockTimeoutMs = 5_000`，`:113`）。无锁回落的诱惑很大（"别阻断用户"），但它的失败模式恰好是这个锁存在的目的 —— 静默丢写入。宁可让一次导入失败并可重试。
3. **锁只保护写，读靠 mtime+size 自检**（`syncWithDisk()`，`:299`）。读写不做互斥（读不加锁），所以读到的可能是"上一次完整落盘"的版本，绝不读到半截文件（因为写是原子的，见 6.3）。

## 6.2 `deletedIds`：防复活的那一手

进程 A 删掉孤儿章节并落盘；A 随后又做一次 `upsert`，它会重新读盘 —— 如果 A 之前只是"内存里删了但当时对方 B 又写了旧内容进来"，孤儿就复活了。更关键的是：**跨进程读到对方写的旧快照时，本进程删除过的文档会混在 `parse()` 结果里回来**。所以 `reload()` 会把 `deletedIds` 里的 id 过滤掉（`src/rag/knowledge_store.ts` 的 reload 逻辑），而 `merge()` 里一旦本进程又写回同一个 id，就把它从删除名单撤销。

这个集合是**有意的内存驻留**：它记住"本进程删过什么"。对几百篇文档无所谓；对几十万篇要设上限，正确做法是记 tombstone（带删除时间的墓碑）而不是永久记录。

## 6.3 Windows 上的 rename：为什么要退避重试

`persist()`（`:375` 起）先写 `${filePath}.${pid}.${Date.now()}.tmp` 再 rename 覆盖目标（`:377`）。两个细节：

- **临时文件名带 pid 和时间戳**：多个进程同时写时不会互相踩临时文件。
- **rename 对 `EPERM/EBUSY/EACCES` 退避重试 4 次**（20ms 递增）。这是 Windows 特有的：目标文件正被另一个进程读时，rename 会**短暂**失败而不是永久失败。Linux 上同名文件 rename 是无条件原子替换，不需要这段。**如果你把这段删了"简化代码"，症状是在 Windows 上偶发导入失败** —— 而且是并发时才有，测试很难覆盖。

坏文件的处理也是同一类纪律：JSON 解析失败时把文件**挪成 `.corrupt-<时间戳>`**（`:327`）再按空库继续，而不是直接覆盖。静默清库是不可恢复的数据损失，留个坏文件只是多占一个 inode。

## 6.4 mtime+size 新鲜度的碰撞窗口

`syncWithDisk()` 用 `mtimeMs !== last.mtimeMs || size !== last.size` 判断外部改动（`:299`）。这是**近似**：

- 同一毫秒内两次写入且大小恰好相同 → 漏检。文件系统 mtime 精度通常在纳秒~毫秒级，且 size 相同是小概率事件，组合起来足够安全。
- 对方写入后**又改回原状**（同 size 同 mtime 精度内）→ 漏检，但内容相同所以无害。

**真正的盲区是**：本进程自己的写入一定会更新 `lastSig`（`persist()` 结尾），否则每次检索都会误判"外部改动"而重载 —— 那会把 stat 的好处变成每次读全量 JSON 的开销。

# 第 7 章 信任分层与加权

## 7.1 层级语义：`internal` 与 `web` 是两种生命周期

`TrustLevel`（`src/rag/knowledge_store.ts:7`）目前只有两级，但它们的差别不是"分数高低"而是**生命周期归谁管**：

| | 过期 | 容量淘汰 | 谁负责删 |
|---|---|---|---|
| `internal` | 永不过期（`isFresh` 只给非 internal 判 TTL） | **不参与淘汰**（`prune()` 里 filter 掉，`:282`） | 导入方（`--sync`，`pruneInternal` `:222`） |
| `web` | 7 天 | 超 `maxDocs=500` 时按 `fetchedAt` 从旧到新淘汰 | 存储自己 |

一个容易忽略的粘性问题：**同一来源先以 internal 导入、之后被联网检索命中同一 URL 会怎样？** `merge()` 里有一行专门处理这个（`:253` 附近）：`existing?.trust === "internal" ? "internal" : input.trust` —— 内部资料一旦标记，不会被后续的低信任写入降级。这条如果漏掉，一次联网就能把你的权威规则文档降级成"7 天后过期"，而且**没有任何报错**。

## 7.2 权重是"推动"不是"置顶"

`trustWeights = { internal: 1.2, web: 1 }`（`src/tools/rag_search.ts:65`），作用在排序键上（`rankOf`），不改 `relevance_score`。两个刻意选择：

- **1.2 倍而非硬性优先**：差距悬殊的词法命中不该被权威等级压掉。测试里专门有一条反证 —— 把 internal 降到 0.5 时 web 能反超，"不是硬性置顶"。
- **不污染输出分数**：返回给模型的 `relevance_score` 是原始 BM25，`trust_weight` 独立字段（`:260` 附近）。混算的后果是调试时分不清"词法强"还是"信任高"，也让任何离线阈值扫参失效（因为分数不再是纯词法的量）。

## 7.3 agent 写入该放哪一层（本项目尚未落地）

计划中的功能是让模型用工具往库里写内容。这引出第三个层级，而它的设计约束是**投毒半径**（详见第 12 章）：

1. **不得并入 `internal`** —— 否则模型生成的文本获得权威外观且永不过期。
2. **应受 TTL 淘汰** —— 与 web 同级或更快过期，限制长期污染。
3. **排序不应高于 web** —— 模型随手写的笔记，凭什么挤掉人工导入或真实网页？
4. **不得覆盖更高信任条目** —— 要在工具层拒绝"用 agent 身份改写 internal 文档"。
5. **返回时必须带 provenance**（"本次会话由 agent 写入"），让模型和用户都能打折。

**状态说明**：`.sand-box/` 里已把 `TrustLevel` 拓到 `"web" | "internal" | "agent"`（`isFresh` / `prune` 改成"非 internal 都受 TTL 与淘汰"），但**尚未覆盖到 src**，`rag_add` 工具与多库切换也停在半路。本节写的是设计约束，不是已交付能力。

# 第 8 章 联网补充与外部分数

## 8.1 最重要的纪律：不做跨体系分数换算

`ingestWeb()`（`src/tools/rag_search.ts:131`）产出的候选分两段排序再拼接（`:180`）：有词法命中的按加权 BM25 排，**词面上完全对不上**的（跨语言场景）按 Tavily 的 `score` 排，两段直接 concat。

诱惑是"取 `0.7*normalize(bm25) + 0.3*score` 这种加权融合"，看起来更优雅。不要这么做的原因：**两个数不可比**。Tavily 的 0.9 是它自己那套外部排序器的产物，跟你的 BM25 分数没有任何共同尺度；一旦换算，你的排序会因为一个无法校准的旋钮而抖动，而线上表现变差时你分不清是哪一路的锅。**分层拼接丑，但可解释、可归因。**

顺带一个真实小坑：同一个 URL 可能在一次 Tavily 响应里出现多次（不同摘要片段），本仓库取**最高分**（`:149-154`）。取平均或取最后一条都会在重复出现时给出漂移的排序。

## 8.2 `use_cache: false` 仍然合并写

语义是"跳过本地检索直接联网"，但**不是**"不要用缓存"。落盘仍走 `upsert`（幂等合并），所以强制刷新不会清空已有积累。这个区分很关键 —— 如果 `use_cache:false` 变成覆盖写，模型每次想"查点新鲜的"都会把你的库洗掉。

## 8.3 首块兜底的条件与代价

新文档入库后，本仓库对它再跑一次本地检索来挑"与查询最贴近的块"；**一篇新文档若一块都没命中，就退回它的首块**（`coverage=0` 的那批，`:167-174` 附近）。为什么必须有：Tavily 已经判定这篇相关，词法对不上很可能正是"中文查询 × 英文文档"，此时返回首块优于返回空 —— 但也可能返回的是一篇毫不相干文章的开头。**这是一个明知会引入噪声也要保召回的取舍**，代价用 `origin` + `coverage: 0` 显式暴露出去，让调试时能一眼看出"这条是兜底来的"。

## 8.4 超时与取消：Bun 的一个真实陷阱

`tavilySearch()` 用 `AbortSignal.any([上层 signal, AbortSignal.timeout(...)])`（`src/tools/tavily_client.ts:55`）。但 **Bun 1.4 的 `AbortSignal.timeout()` 定时器不 ref 事件循环**：如果这是唯一的待办事项，进程可能先退出而超时永不触发（`:58-62` 补了一个会 `clear` 的同长度定时器兜底）。这类运行时差异不体现在类型检查里，只能靠实测和注释留住。

另外两条纪律：**上层取消原样抛**（不翻译成检索错误，否则 Agent 会把用户 Ctrl+C 当成"网络失败"重试），**联网失败时若已有本地结果就带着 `web_search_error` 返回**，两者皆空才抛错 —— 返回空数组是最坏选择，模型会把"我没查到"理解成"世界上没有"。

## 8.5 遗留的策略问题

现在是"本地命中数 < `top_k` 就打 Tavily"（`src/tools/rag_search.ts:232` 的判断）。这有两个后果：每次查询不足 top_k 都消耗配额；以及外部文本会持续进入结果集（与第 12 章投毒面直接相关）。改成**"仅零命中才联网"**会省配额、也让内部语料不被外部文本稀释，但会牺牲"多要几条相关结果"的能力。**尚未决定**，因为它取决于你希望 `rag_search` 主要服务内部规则还是外部情报 —— 而这恰好是当前库里的实际情况（只有 MCP 文档）与工具描述（反诈资料）不一致的地方。

# 第 9 章 向量与混合检索的工程细节

> 本章内容本仓库**全部未实现**。写的是"真要上向量时你会撞上什么"，避免把这一章读成进度汇报。

## 9.1 模型选择之后立刻遇到的三件事

1. **维度与存储**：1024 维 float32 = 每向量 4KB。**10 万块 = 400MB**，纯内存。这就是量化（int8 约 1/4 体积、PQ 可到 1/16~1/64）和"向量单独旁挂文件、别混进 JSON"存在的理由 —— 本仓库现在的 `knowledge.json` 若直接塞向量，会变成一个几百 MB、每次 rename 全量重写的大文件，把第 6 章的原子写变成性能灾难。
2. **归一化**：多数 embedding 服务返回未归一向量，需要 L2 归一后点积才等于余弦。**入库和查询必须做同一套**，否则分数尺度会漂。
3. **版本一致性**：换 embedding 模型 = 全库重算。你必须能回答"哪些块是用哪个模型版本算的"，否则新旧向量混在一个索引里，相似度数字之间的比较毫无意义。字段级解法：doc/chunk 上记 `embeddingModel` + `contentHash`，只对变更或版本不符的块重算 —— 这和第 5.3 节"分词缓存的失效判据是内容"是同一个道理。

## 9.2 ANN 参数怎么调（以及要盯什么指标）

| 索引 | 关键旋钮 | 调大的效果 / 代价 |
|---|---|---|
| HNSW | `efConstruction`（建索引）、`efSearch`（查询） | 召回↑ 延迟↑；内存基本不变 |
| IVF | `nlist`（簇数）、`nprobe`（查询探测簇数） | `nprobe`↑ 召回↑ 延迟线性↑ |
| 量化 | PQ 子空间数 / int8 | 体积↓ 召回↓，需要重排（rerank 原始向量）补救 |

**必须盯的两个数**：**召回率@k**（用暴力扫描的真实 top-k 当 ground truth 对比）和**每查询延迟 p99**。只看平均值会被尾部骗 —— RAG 场景里一次漏检直接导致一次错误回答。

## 9.3 RRF 不是免费的

RRF 的 `k`（惯例 60）控制"名次衰减快慢"：k 小则头部名次权重极大，k 大则趋于平均、各路排名差异被抹平。它免掉了归一化，但**引入了对候选列表长度的隐式假设**：某一路只返回 5 条、另一路返回 50 条时，短列表里的差名次可能拿不到贡献 —— 需要显式补齐或统一候选池大小。

替代方案：convex fusion（`α·归一化词法分 + (1-α)·归一化向量分`）。它更可控，但归一化本身就是需要校准的坑。**建议路径**：先 RRF（免调参、可解释），有了评测集再拿它当基线试 convex fusion。

## 9.4 精排与多样性的成本模型

cross-encoder rerank 每条候选一次前向（本地几百 ms 级、外呼则计费和网络延迟）。**延迟预算**：`top 50 候选 × 10ms = 500ms` 就已经是纯检索开销。工程上常见的分级是：BM25 出 100 → 向量出 100 → RRF 合成 ~80 → cross-encoder 精排出 20 → MMR 去重取 5。

**MMR（最大边际相关）**解决"5 条结果其实是同一篇文档的 5 个近似块"。这与第 4.3 节的 `maxChunksPerDoc` 是同一问题的两种解法：硬上限（便宜）vs 相似度惩罚（更准但要算块间相似度）。本仓库目前是硬上限路线，够用。

# 第 10 章 查询理解与路由

## 10.1 改写是检索质量里性价比最高的一块

对话式提问天然不适合直接检索（"那这个呢？""平台会怎么处理"）。三个层次，成本递增：

1. **抽取式压缩**：把问题压成 3~5 个高 IDF 关键词。零模型调用也能做（用现成语料 IDF 挑词），且直接改善第 4.1 节的覆盖率失真。
2. **上下文补全改写**：用一次便宜的模型调用（本仓库已有 `summaryModel: "qwen3.6-plus"` 这类注入模式，见 `src/index.ts` 的 Agent 配置）把对话历史压成一句自足的问题。
3. **多查询扩展 / HyDE**：分别检索后 RRF 合并 / 先假想答案再拿答案向量检索。**必须等向量存在才有意义**。

**顺序建议**：第 1、2 层在纯词法阶段就能吃，收益立现；第 3 层属于向量时代的配套。

## 10.2 路由到"哪个库"：先要有库的概念

需求是"rag_search 可以换不同的知识文档"。两种设计：

| 方案 | 做法 | 代价 |
|---|---|---|
| **命名空间过滤**（推荐） | 单一存储不变，`kb` 名字 → source 前缀 + trust 过滤。现在 `internal://docs/平台规则/` 这类前缀天然就是库的边界，`pruneInternal(prefixes)` 已经证明按前缀做集合运算是成立的 | 不能单独导出/整体替换某库；跨库检索要合并打分 |
| **物理多库** | 每库一个 `KnowledgeStore`（独立文件/锁/索引） | 检索要扇出 + 归并；每库一份锁与索引；`revision` 语义变成多个 |

**一条不可让步的边界**：`kb` 必须是**启动期注册的白名单名字**，模型只能从枚举里选，永远拿不到路径。本项目的路径守卫只覆盖 MCP 工具（`src/mcp/adapter.ts:86`、`src/index.ts:94`），本地工具是宿主进程内直接执行 —— `rag_search` 现在之所以安全，是因为 `cacheDir` 由代码固定、没有任何来自模型输入的路径（第 12.3 节）。**加了可配路径的本地工具，就是主动放弃这个前提。**

## 10.3 澄清式检索：项目里已有可复用的机制

问题太模糊时，正确动作是**反问**而不是硬检。MCP 规范里的 elicitation（表单式追问）本仓库已有实现基础（`src/mcp/cli_confirmer.ts` 的 form 模式：按 `requestedSchema` 逐字段问，无 schema 时退化 y/N）。本地工具层如果要做澄清，可以复用同一个 Confirmer 签名，而不是新造一套交互 —— 但要注意：**非交互环境（管道/CI）下必须能干净拒绝或走默认值，绝不能挂起等输入**。这一点在会话选择逻辑里已经处理过一次（`src/index.ts` 的 `chooseSession` 对 `stdin.isTTY` 分支的判断）。

# 第 11 章 评测工程

## 11.1 20 条评测集比一套框架有用

造集的现实路径（成本从低到高）：

1. **从真实使用里挖**：把历史上"检索结果被采纳 / 被模型引用"的 `(查询, chunk_id)` 对自动落成 golden set。本仓库已有 trace 所需的字段（`chunk_id`、`coverage`、`relevance_score`、`trust`），**只差把每次调用记下来**。
2. **让 LLM 从文档反向生成问题**：给每块让模型出 2~3 个"这段能回答的问题"，(问题 → 该块) 就是天然配对。缺点：分布偏乐观（问题就是照着答案生的），必须**人工抽查剔除太容易的样本**。
3. **真实用户问句 + 人工标注**：最贵也最真。

存成仓库里的 `eval/dataset.jsonl`（一行一个 `{query, expected_chunk_ids, expected_sources}`），格式自选，关键是**能被 `bun test` 读**。

## 11.2 指标可以直接在测试里跑

```
recall@k = Σ 命中正确块的查询数 / 查询总数
MRR      = Σ (1 / 正确块首次出现的排名) / 查询总数
```

把它们写成 `tests/rag_eval.test.ts`，**打印当前值 + 设下限断言**（比如 `recall@3 >= 0.7`）。这样做的价值：任何改动分词、切块、阈值、权重的重构，都会在 CI/本地测试里立刻告诉你检索变差了 —— 这是第 1.2、5.1 那类"静默退化"唯一的系统性解药。

**注意指标陷阱**：
- **先只测检索，别测端到端**。端到端准确率 = 检索质量 × 生成质量，两者会互相掩盖。
- **k 要匹配实际用法**。你只把 top-3 塞进提示，就用 recall@3；报 recall@20 是自我安慰。
- **样本量小就别追显著性**。20 条集上 +1 条命中就是 +5%，别把这种波动当改进。**改进要能解释机制**（"因为加了 title 加权"），数字只是佐证。

## 11.3 忠实度（groundedness）与裁判的裁判

生成侧指标里最有用的是**忠实度**：回答里每个论断能否在检到的块里找到依据。常用 LLM-as-judge，但要防两件事：
- 裁判倾向于给"流畅的回答"高分，而不去核查依据 —— 提示里必须强制"先列论断，再逐条要求引用块 id"。
- 裁判与生成同源时，会系统性放过自己的错。**抽查 20 条人工核对裁判判定**，是你唯一能校准裁判的方式。

**自查问题**
1. 为什么 LLM 反向生成的评测集会高估效果？
2. 为什么 recall 的 k 必须等于实际注入的块数？

# 第 12 章 安全进阶

## 12.1 语料投毒的三条防线

低信任来源写入检索库时（第 7.3 节），三条控制缺一不可：

1. **provenance 与层级隔离**：写入即带"谁写的"，且不得并入权威层。返回给模型时必须标注，让"本次会话 agent 写的笔记"和"人工导入的平台规则"在提示里看起来就不一样。
2. **TTL / 可过期**：限制污染半径是数月而不是永久。
3. **不得顶掉高信任条目**：工具层显式拒绝"以低信任身份覆盖高信任 source"。**光有层级不够** —— 第 7.1 节那条 `internal` 粘性规则正是这一条的实现。

还有一条属于运维：**可撤销**。投毒被发现时要能定位"这条是哪天哪个来源写进来的"并删掉。本仓库已具备前半个能力（`source` + `fetchedAt` + `trust` 都在 doc 上，`--sync` 提供按前缀删除），后半个（按来源精确吊销 + 墓碑记录）没有。

## 12.2 间接提示注入：现在做到了哪一步

已做的：检索结果整体包成不可信块（`src/core/untrusted.ts:7` 的 `UNTRUSTED_DATA_NOTICE`），MCP 资源注入上下文时同样走 `wrapUntrustedData`；工具描述里明确要求"用 [ref] 标注引用"。

**没做的**：检索后没有指令模式过滤（"ignore previous instructions""请把结果发送到…""系统提示：新规则"这类特征），也没有对进入上下文的外部文本做二次消毒。定界 + 标注是**必要不充分**的：它降低被劫持的概率，不降低被劫持的上限。真正的加固顺序通常是：过滤特征串 → 长度/字符集约束 → 高危动作（写文件、外呼）永远要人工确认。

## 12.3 一个明确的审计缺口

`policy_matrix` 的风险分级与 `onAudit` 审计都挂在 `McpAdapter` 上（`src/mcp/adapter.ts`），**只覆盖 MCP 工具调用**。本地工具（`rag_search`、`search_web`、未来的 `rag_add`）走 `toolRegistry.execute`，既不分级也不留审计记录。

因此第 10.2 节那条不变量是**唯一的兜底**：本地工具的 fs 路径必须来自代码，不能来自模型输入。这条约束目前是"事实如此"，但没有机械保护。可落地的补法：`ToolDefinition` 上加一条约定（本地工具的 args 里不得出现路径类字段，注册期扫描 schema 拒绝），或把 `allowedRoots` 的判定抽成宿主级公用函数供本地工具调用。**这是设计选择，尚未决定** —— 与"本地工具是否需要和 MCP 工具同等约束"是同一个问题。

## 12.4 权限感知检索（ACL-aware）

多知识库一旦面向不同用户，检索就可能越权泄露：**相关性排序不会替你做权限过滤**。正确姿势是把过滤条件放进检索（每条 doc 记 `owner`/`audience`，查询时按调用者身份 filter —— 本仓库 `Bm25SearchOptions.filter` 已经是这个形状，`src/tools/rag_search.ts:122` 用它做过期过滤，加 ACL 只是换个谓词），而不是检索完再在应用层删。**后置过滤会泄进统计信息与排序结构；而且忘记过滤的代价是数据泄露而不是效果下降。**

# 附录：调试手册 —— "这条为什么没搜到"

按顺序排查，每步都有可执行动作：

1. **块在不在库里？**

```bash
bun -e '
import { KnowledgeStore } from "./src/rag/knowledge_store";
const docs = await new KnowledgeStore({ filePath: ".rag-cache/knowledge.json" }).list();
console.log(docs.length, "篇：", docs.map((d) => d.source).join("\n"));'
```
   → 不在：是 `--sync` 的孤儿清理误删，还是从没导入？
2. **是不是过期了？** 看 `trust` 与 `fetchedAt`：`web` 超 7 天即不新鲜，会被 `filter` 挡掉（`src/tools/rag_search.ts:122`）。
3. **是不是被覆盖率阈值砍了？** 用入门篇 12.2 那段脚本，去掉阈值直接看 `coverage` 分布。低于 0.25 说明"字面重合度不够"，考虑 4.1 的三种失真或第 6 章的跨语言。
4. **是不是分词没对上？** 分别打印 `tokenize(块文本)` 和 `tokenize(查询)` 求交集。**交集为空就是分词/字形问题**（1.3 的繁简、大小写、全角），不是排序问题。
5. **是不是被 `maxChunksPerDoc` 挤掉了？** 同一篇的多个块都命中时，只有 2 条能进（4.3）。
6. **是不是标题才有的信息？** 查一遍整篇标题里有没有那个词 —— 若有，就是 2.2 的字段加权缺口。
7. **库里根本没有相关文档？** 最常被跳过的一步：以上全部正常时，答案往往是"没导入"或"这个问题就不该问词法检索"（第 6/9 章的向量场景）。

**最后一条经验**：RAG 的疑难问题里，**排序调参占少数，数据本身占多数**。先确认库里有什么、什么形状，再动权重和阈值 —— 顺序反了你会开始调一堆根本不相关的参数。
