# 任务持久化与独立验收

这一版在现有 Agent 上加入独立任务记录和确定性文件验收，没有引入 A2A 或额外模型。CLI 与 Web 使用相同执行路径。

## 使用方式

正常发送目标开始任务；后续消息会接续当前未验收或未完成任务，保留原目标、计划、历次要求和工具执行记录。通过验收的任务结束，下一条普通消息自动创建新任务。

需要主动切换目标时，在 CLI 或 Web 聊天框输入：

```text
/task new 新的任务目标
```

旧任务保留为 `superseded`，不会被删除，也不会冒充已完成。`/task` 或 `/task status` 查看当前状态，不调用模型。

Web 右栏显示保存的任务、计划、验收条件、实测结果和待核对操作；刷新或重启后从任务库恢复。`GET /sessions/:id/history` 包含当前任务，`GET /sessions/:id/tasks` 可查询该会话全部任务。

## 独立验收的含义与边界

模型通过 `set_acceptance_criteria` 声明验收条件；宿主也可以通过 `AgentConfig.acceptanceCriteria` 预设条件。模型不能提交“验收通过”，也不能修改已经登记的条件。模型声明条件须在业务工具执行之前，避免按照已经生成的结果降低标准。

宿主独立读取 `verificationRoot` 工作区内的真实文件，执行以下检查：

| 检查 | 条件 |
| --- | --- |
| `file_exists` | 普通文件存在，字节数达到 `minBytes`，默认至少 1 字节 |
| `text_contains` | 文件正文包含指定的非空文字 |
| `json_equals` | JSON 中 `keys` 指定的字段与 `expected` 严格相等；空 keys 检查整个 JSON |
| `sha256` | 文件散列与指定 SHA256 一致 |

例如要求写入特定内容，可登记：

```json
{
  "criteria": [
    {
      "kind": "text_contains",
      "path": "report.txt",
      "description": "报告包含用户指定结论",
      "text": "本次审查证据不足"
    }
  ]
}
```

检查只支持不超过 5 MB 的普通文件。拒绝越界路径、符号链接、凭据与受保护目录；不会执行模型生成的验收脚本。每项结果记录检查说明、路径和通过与否；成功读取的文件还记录 SHA256，整组结果记录检查时间。

**验收通过仅表示所列条件实测通过，不代表已经证明所有自然语言要求或业务结论正确。** 尤其是“文件存在”不能证明报告质量，JSON 字段为某值不能证明该判断符合事实。重要工作由宿主提供与用户目标匹配的条件；没有合适的检查器时保留“已回答，未验收”。当前没有通用的代码测试运行器或网站审查语义评分器。

**条件是谁提的，结果就按谁的口径读。** CLI 与 Web 右栏都标注验收条件来源（宿主设定 / 模型自设），模型自设条件全部通过时的通知也点明“标准由模型提出”。要求只认宿主设定时设 `AGENT_REQUIRE_HOST_CRITERIA=1`：模型仍可登记条件、宿主照常实测，但任务停在“已回答，未验收”，不亮“验收通过”。

不管任务怎么收尾，只要登记了条件就实测一次并留下证据——未完成、超预算、模型拒绝同样能看到“文件实测不存在”这类客观结果，而不是空白的“待验收”。被取消的那一轮不读盘：中断会被检查器记成“实测不符合”，那是假证据。

模型正常结束、计划没有待办、全部条件通过，才得到 `taskStatus: verified`、`stopReason: verified_answer`，持久化任务进入 `completed`。普通完整回答仍为 `answered`；兼容字段 `success: true` 表示回答成功或验收通过，**要求独立验收的调用方必须检查 `taskStatus === "verified"`**。

验收失败先向执行模型反馈一次实测问题，允许在已有迭代与预算内修复；最终再独立检查一次。失败结果为 `verification_failed`，不会报告任务完成。计划未完成、拒绝、截断、预算用尽与取消不会被文件检查覆盖为成功。

## 存储与续跑

每个会话使用 `.agent-sessions/tasks/<sessionId>.sqlite`（会话目录可配置）。SQLite 事务保存：

- 独立 task ID、原始目标、工作区和生命周期状态。
- plan、验收条件及来源、验收结果与证据散列。
- 每次 run 的 ID、用户补充要求、起止时间和结束原因。
- 每个工具操作的 ID、参数、开始记录、返回摘要和人工核对记录。
- 等待人工输入或脚本确认的提示。原有 MCP 的独立审批仍由 UiBridge 管理；工具的在途记录保证中断后不会静默重放。

计划在工具返回时持久化；每次继续执行前恢复。最近任务摘要钉入上下文，较早的指令和工具返回摘要可以通过 `read_task_state(offset, limit)` 分页回读。任务记录与聊天压缩、文件检查点分别管理；回滚文件不会回滚任务账本，下一次验收会读取回滚后的真实文件。

工具执行前先提交开始记录，执行后提交返回记录。`returned` 只表示拿到了返回值，可能包含错误，不等于操作成功或通过验收。完整的大工具结果仍按既有工具输出机制保存，本任务账本只保存最多 2000 字符摘要。

每个工具自己声明中断后是否需要人工核对（`ToolDefinition.needsReconciliation`，缺省按需要，最保守）：只读工具、以及只写自有幂等存储的工具（检索索引、任务账本、计划）无需核对；MCP 工具按 `readOnlyHint`／`destructiveHint`／`idempotentHint` 推导。结果不可确认时，需要核对的工具标 `unknown`，其余标 `no_effect`（收口留痕，但不打断续跑）。

同一会话有运行中的任务时拒绝并发执行，其他会话独立运行。运行所有者进程退出后，读取任务会标记为 `interrupted`。不能确认结果的在途操作标为 `unknown`；此时不调用模型、不重放工具，也不能通过“新任务”跳过核对。**中断的那一轮里已经返回的有副作用操作同样转为待核对**：跨进程续聊只保留完整对话轮，模型看不见那一轮的工具调用，不核对就可能把同一次外部写入静默地重做一遍。

在检查真实文件或外部状态后，用户可输入：

```text
/task resolve 操作ID applied 已核对实际结果，操作已经执行
/task resolve 操作ID not_applied 已核对实际结果，操作没有执行
/task resolve all applied 已逐条核对实际结果
```

前两条命令由宿主处理，不提供为模型工具；`all` 用同一句说明一次收口全部待核对操作。确认已执行的同工具、同参数操作会阻止原样重放；确认未执行后允许重新尝试。核对全部未知操作后再发送“继续”。这属于人工核对后的续跑，不是任意外部副作用的 exactly-once 保证。

该轮没有需要核对的副作用时，中断可以直接续跑。等待输入的内存回调不会跨进程复活，也不会自动恢复过往批准；必要时重新发起交互。工作区改变时不能静默沿用旧任务，需要切回原工作区或显式新建任务。

直接构造没有 SessionStore 的 Agent 时，默认任务仓为内存态；需要落盘的嵌入式调用方应提供 SessionStore 或带文件路径的 TaskStore。

## 验证

`tests/task_lifecycle.test.ts` 覆盖真实文件读取、错误完成声明、自动修复、验收条件不可降低、跨 Agent 实例恢复、会话隔离、进程退出后的未知副作用、返回之后才中断的重复执行拦截、无副作用工具取消后可直接续跑、`/task resolve all` 一次核对全部、非正常收尾仍留实测证据、宿主策略不采信模型自设条件、取消、磁盘写入失败与人工交互记录。模型响应均为本地模拟。

`web/tests/run_outcome.test.ts` 覆盖验收状态显示、历史与重连后的计划恢复；`tests/session_config.test.ts` 覆盖任务事件只转发一次；旧的运行状态、拒绝识别、配置与计划测试继续保留。
