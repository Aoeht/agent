# 子 Agent 运行时：任务契约、复核与定向补查

宿主协调层直接创建和管理子 Agent。协调模型通过 JSON 计划描述任务及交付要求，调度器调用 `new Agent()` 和 `Agent.run()`；独立复核 Agent 检查结果，宿主最多安排两轮定向补查。主对话另有轻量委派工具 `delegate_task`（`src/tools/delegate_task.ts`，2026-10-24）：单次派出一个只读白名单子代理调研/复核并把报告经围栏回注本对话，与本运行时共用 `createTeamRegistry` 白名单与能力声明；多任务 DAG、独立复核与定向补查仍由本运行时承担。

`delegate_task` 默认开启，`AGENT_DELEGATE=off`（或 `0`/`false`/`no`）在启动层面整体关闭——工具不再注册，Web 会话的工具开关此时也无可关项；scanner 委派（见 docs/视频诈骗扫描.md）随之不可用。会话内临时停用仍用 Web 工作台的工具开关，只影响当前会话。本节其余内容（团队运行时）不受该开关影响。

## 使用

沿用项目的 `.env` 模型配置和 MCP 工作区配置，在项目根目录运行：

```powershell
bun run team "阅读工作区代码，分析任务生命周期实现，再核对失败恢复的边界"
```

也支持管道输入和帮助：

```powershell
"对比工作区中的两份方案，列出差异和缺失信息" | bun run team
bun run team --help
```

终端打印任务启动、结束、复核意见、补查轮次及汇总状态。按 Ctrl+C 取消整个运行；取消信号传给规划、汇总、复核和所有已经启动的子 Agent，等待它们清理后退出。默认整个协调运行最多 10 分钟，不包含启动 MCP 服务的时间；每个子任务（含复核）另有墙钟上限，取 `AGENT_TEAM_CHILD_TIMEOUT_MS` 与团队剩余时间的较小值，超线任务按 `max_wall_clock` 停止并判失败，可被复核要求补查。

模型接口需要支持 OpenAI 兼容的 Chat Completions、JSON object 输出和普通工具调用。协调调用的传输类错误（连接中断、429、5xx）会指数退避自动重试，最多 3 次尝试；规划输出不合法时会携带宿主校验错误重试一次。重试耗尽、被拒绝或被截断时明确失败，不会把残缺计划当作可执行任务。

入口是独立的一次性 CLI；原有单 Agent CLI 和 Web UI 保持现有行为，尚未增加 Web UI 团队任务面板。

## 执行流程

```text
用户目标
  → TeamCoordinator：规划（JSON，无 tools 参数）
  → 校验任务数量、角色、ID 和完整依赖图
  → AgentScheduler：为就绪任务预留预算、分配并发槽位
      → Agent A：独立上下文、工具注册表、计划和任务账本
      → Agent B：独立上下文、工具注册表、计划和任务账本
      → Agent C：等待指定依赖成功回答后再执行
  → 独立复核 Agent：核对原始要求、证据和未解决问题
      → 有具体缺口：重跑相关任务及下游，再复核（最多两轮补查）
      → 全部通过、需要外部条件、预算/轮数耗尽：结束闭环
  → TeamCoordinator：汇总最新结果和最终复核意见（无 tools 参数）
```

计划格式：

```json
{
  "tasks": [
    {
      "id": "collect", "role": "researcher", "goal": "分析退出流程", "dependsOn": [],
      "deliverables": ["退出接口调用链与对应证据"],
      "checks": [{ "id": "logout", "description": "检查退出后旧 token 是否失效" }]
    }
  ]
}
```

角色可以是 `researcher`、`analyst`、`reviewer`。角色描述任务分工，不授予额外权限。任务 ID 必须是小写字母开头的字母、数字、下划线或连字符，最多 40 字符，且不能使用保留名 `team-review`（宿主独立复核占用，规划占用该 ID 会被拒绝并要求重试）。未知字段、重复 ID、不存在的依赖、自依赖、循环依赖和超量任务都会在创建子 Agent 前被拒绝。

每个任务包含 1–6 个交付项和 1–6 个检查项，检查项 ID 在任务内唯一。初始计划确定后，补查不能修改这些标准。宿主额外安排独立复核，因此不必为了这一流程在计划中再创建一个总复核任务。

调度器在任一子任务结束后立即复用空闲槽位。任务失败或被拒绝后，该轮下游标为 `skipped`，其他独立分支继续；独立复核可以指出可补查的问题，下一轮重新执行相关分支。父任务取消后不再启动新任务。

## 结构化交付与复核闭环

工作子 Agent 最终返回 JSON，字段包括：

- `summary`：结论。
- `deliverables`：按原清单的 `index` 逐项给出交付内容；无法完成时说明原因。
- `findings`：发现及其 `evidenceIds`。
- `evidence`：证据 ID、实际查阅的来源位置和片段。
- `coverage`：每个检查项的 `covered/missing`、关联发现及说明。
- `unresolved`：未解决问题。

例如一个检查项的 `coverage` 可以是 `{"checkId":"logout","status":"covered","findingIds":["f1"],"note":"已核对撤销实现"}`。只有存在 `f1`，且其引用的证据也存在，结构校验才接受 `covered`。解析前会做容错提取：接受 Markdown 围栏和前后夹杂的说明文字，但提取后仍走完整的 JSON 解析与 Schema 校验。遗漏交付项、减少检查项、重复 ID 或引用不存在的发现/证据，都会使该次子任务标为失败，原始回答仍保留供复盘。

结构校验失败时，宿主先给该任务安排一次**无工具的格式修复子运行**：重放上一次的最终回答和具体校验错误，要求只修正输出格式（轨迹与账本文件带 `-repair` 后缀，不覆盖原运行）。修复成功则按新输出重新校验并接受，token 消耗并入原任务的预算结算；修复仍失败才把该任务标为失败，留给独立复核提出补查。

独立复核使用一个全新的只读 Agent，可以重新读取原始资料。设置 `AGENT_TEAM_REVIEW_MODEL` 可以让复核（含其格式修复）运行在与工作任务不同的模型上，获得跨模型的独立性；留空时两者使用同一模型。它必须对每个原始任务的每个检查项给出一次判断：

- `pass`：说明依据，引用该检查项关联的证据。
- `needs_work`：指出缺口，并给出要补查的问题及需要的证据。
- `blocked`：说明所需的外部材料或权限，不能只要求“再试一次”。

宿主校验复核覆盖范围和证据引用。复核模型即使返回 `pass`，但工作任务失败、覆盖状态仍是 `missing`、引用证据不对应检查项，或仍有 `unresolved`，宿主都会将该项降为 `needs_work`。复核 JSON 格式错误或引用不存在的证据时，复核本身失败，不能自动补成通过；复核失败（含格式修复未成功）时预算允许会先原样重试一次，两次都失败才判定复核失败并结束运行，两份尝试都保留在 `reviews` 中。

这套校验保证结构和引用关系完整，**不证明来源真实、片段准确或推理正确**；复核依然是模型评审，不等同于独立文件验收或测试执行。初始交付要求也由协调模型制定，应结合真实任务评测检查其是否覆盖用户目标。

补查按复核中的具体缺口选择原始任务，重跑它们及所有依赖它们的下游任务，防止沿用旧结论。无关分支保留结果。补查 Agent 获得原始标准、上次提交、直接依赖的最新结果和对应反馈，返回完整的新提交。反馈按 `taskId` 标注来源：除自己的未通过检查项外，下游任务还会附带被返工的直接依赖的检查项，说明上游结论为何不可靠，以便针对性重新核对。每轮重新创建 Agent，不复用旧上下文或任务账本。最终汇总只使用各任务最新版本；所有旧版本仍保存在报告中。

最终汇总输入使用专用紧凑投影：每个任务只带结论、交付内容、未解决问题和来源定位（URL/文件路径，不含证据片段），不复述 findings、coverage 或重复的摘要文本；独立复核压缩为结论加未通过项（带原始检查项说明和补查要求），通过项只保留数量。汇总输入超出协调预留时逐级收紧（先去掉引用列表，再按每任务 4000/1600 字符限长裁剪，裁剪顺序为未解决问题 → 来源 → 交付内容 → 结论），被裁内容以 `…(截断)`/`truncated` 如实标注，并要求汇总模型不臆测被截断的内容；这样多任务大提交也不会让汇总因预算不足而整体失败。

默认最多两轮补查，即初次执行加两轮补查、最多三次独立复核。只有 `blocked` 而无可执行补查项时直接结束。预算不足、复核失败或两轮后仍有缺口，返回 `incomplete`，不会靠汇总文本改变运行状态。

## 隔离与权限

每次子任务创建全新的 Agent、ToolRegistry、PlanStore 和 TaskStore。原始用户目标、分配的任务要求和直接依赖的结构化结论进入子任务上下文；复核 Agent 接收全部任务的最新结构化提交。结果、反馈和证据使用不可信数据围栏，完整工具历史留在各自轨迹中。结构化结果保留 ID 和引用关系；格式异常的原始文本作为诊断数据最多注入 6000 字符。

子任务之间共享底层模型客户端和 MCP 连接，但不共享对话历史、计划或任务控制器。MCP 的路径守卫和策略仍然生效。

宿主明确允许以下能力：

- 已挂载的 `search_web`、`rag_search`、`git_tree`、`read_image`。
- `filesystem` 的文本读取、批量读取、目录列举、目录树、文件搜索、文件信息和允许目录查询。
- 每个子 Agent 自己的 `update_plan`、`read_task_state`。

没有文件修改、脚本执行、浏览器操作、技能执行、外部消息发送或继续派生 Agent 的能力。只读指业务能力；运行记录、任务账本及检索缓存仍会写入本地。MCP 工具声明自己可并行或只读，不会自动获得白名单权限。

目前不转接交互式追问和审批，MCP 策略要求审批的调用仍会被拒绝。模型缺少资料时应报告限制；写代码或其他超出能力的目标只能得到分析方案，不能当作已经完成实际修改。

## 配置和预算

团队运行沿用 `AGENT_MODEL`、`AGENT_SUMMARY_MODEL` 和温度。子任务最多 24 次迭代；如果 `AGENT_MAX_ITERATIONS` 设置了更小的正数，则使用更小的值。团队预算使用以下独立配置，不继承单 Agent 的 token/工具次数配置：

| 环境变量                             |    默认值 | 含义                     |
| -------------------------------- | -----: | ---------------------- |
| `AGENT_TEAM_CONCURRENCY`         |      2 | 同时运行的子 Agent 数量，范围 1–8 |
| `AGENT_TEAM_MAX_TASKS`           |      6 | 计划最大任务数，范围 1–8         |
| `AGENT_TEAM_TOTAL_TOKENS`        | 150000 | 团队 token 预算            |
| `AGENT_TEAM_CHILD_TOKENS`        |  24000 | 每个子任务启动前预留的 token 配额   |
| `AGENT_TEAM_CHILD_TOOL_CALLS`    |     20 | 每个子任务最多工具调用次数，范围 1–100 |
| `AGENT_TEAM_COORDINATION_TOKENS` |  18000 | 规划和汇总各自预留的 token 配额    |
| `AGENT_TEAM_COORDINATION_MAX_TOKENS` | 4096 | 协调调用单次输出上限，范围 256–32768；服务商支持更大输出时可调高 |
| `AGENT_TEAM_TIMEOUT_MS`          | 600000 | 协调运行超时，范围 1–3600000 毫秒 |
| `AGENT_TEAM_MAX_REWORK_ROUNDS` | 2 | 最多补查轮数，范围 0–2；0 仍进行首次独立复核 |
| `AGENT_TEAM_REVIEW_MODEL` | （空） | 独立复核子 Agent 使用的模型；留空用 `AGENT_MODEL`，建议配置不同家族的模型 |
| `AGENT_TEAM_CHILD_TIMEOUT_MS` | 0 | 单个子任务墙钟上限（毫秒），范围 0–3600000；0 表示仅按团队剩余时间派生 |

补查轮数允许 0，其他数值必须是正整数。总预算至少容纳一次规划、一次汇总、一个工作子任务和一次独立复核。汇总配额在规划前预留，每轮工作执行前另外预留复核配额；并发子任务先预留再执行，完成后按实际报告的消耗结算并退回未用额度。复核使用与工作子任务相同的 token 和工具次数限额。所有轮次、所有复核与规划汇总共用同一预算，补查不会重置额度。预算不足时先等待活动任务结算；仍不足则跳过待运行任务或结束补查，并保留最终汇总配额。汇总输入按 token 估算逐级收紧，确保装进 `AGENT_TEAM_COORDINATION_TOKENS` 并给汇总补全留下至少 512 token。

预算沿用现有 RunBudget 的逐请求/逐步骤检查语义，**不是模型服务账单的严格上限**：已发出的单次请求、上下文压缩和收尾可能越过配额；活动请求也不能撤销已产生的费用。协调调用使用模型 usage，缺失时估算并在结果中标记；协调调用的传输重试按各次尝试累计计费，请求已发出但从未拿到响应时保守按预留额度结算，未发出的请求不扣费。子 Agent 消耗沿用现有 AgentResult 的 usage 记账。第一版不允许子任务自行申请追加额度。

## 结果、记录与边界

默认保存到 `.agent-sessions/teams/<runId>/`，设置 `AGENT_SESSION_DIR` 可更改存储根目录：

```text
events.jsonl       团队启动、完整计划、各轮子任务、复核反馈、补查安排和终态
result.json        所有工作尝试、独立复核、补查轮数、最终答复、累计 token
tasks/<mode>-r<round>-<id>.sqlite  各次工作/复核的独立任务账本
traces/           每个子 Agent 的模型步骤、工具记录和运行结果
```

`parentRunId` 将子任务关联到团队运行，`mode` 区分 work/review，`round` 从 0 开始；子任务记录还保存自身 Agent 的 taskId/runId。`tasks` 保留各轮工作尝试，`reviews` 保留独立复核，`reviewStatus` 表示当前复核状态，`reworkRounds` 表示启动的补查轮数。任务文件和轨迹名包含模式及轮次，不覆盖上一轮。团队事件逐条落盘；事件记录失败会告警，最终报告写入失败会以错误退出。运行结束时终端还会打印一张小表，列出每次工作/复核尝试的模式、轮次、状态、token 消耗与失败原因，累计为估算时注明。记录可能包含用户资料，不应提交到代码仓库；默认目录已在 `.gitignore` 中。

团队终态：

- `answered`：各工作任务的最新提交完整，最终独立复核全部通过，汇总也成功。**不代表独立验收通过**。
- `incomplete`：部分任务失败、跳过、超时、超预算，或最终汇总失败。已获得的子任务结论仍保留。
- `cancelled`：用户取消。
- `failed`：未能完成规划等启动阶段。

只有 `answered` 退出码为 0；取消为 130；其他未完整结束的情况为 1。汇总模型即使声称全部完成，也不能覆盖调度器记录的失败状态。数字引用编号属于各子任务，最终汇总要求使用真实 URL/文件路径，避免把不同子任务的 `[1]` 混为同一来源。

支持固定任务要求和有向无环依赖，能根据复核反馈有限重跑相关任务；不支持自由追加任务或修改标准、跨 Agent 实时消息、持久运行恢复、跨进程工作节点或 A2A。运行记录可供复盘，重新执行命令会开始新团队，不会自动恢复旧团队。

## 代码与验证

- `src/core/team_contracts.ts`：任务契约、结构化结果、复核协议、容错 JSON 提取及引用完整性检查。
- `src/core/team_coordinator.ts`：模型规划（含格式重试）、独立复核、定向补查、结果汇总、团队级超时和预算。
- `src/core/team_scheduler.ts`：DAG 校验、预算预留、调度、子任务生命周期和一次性格式修复。
- `src/core/llm_retry.ts`：LLM 传输类错误判定与退避延迟计算，单 Agent 与协调层共用。
- `src/team_runtime.ts`：工具白名单、子 Agent 装配、团队环境变量。
- `src/team.ts`：一次性 CLI、信号处理和运行记录。
- `tests/team.test.ts`：调度并发、依赖失败、取消、预算、协议错误、修复运行、汇总投影、隔离和真实 Agent 循环的假模型测试。
- `tests/team_review.test.ts`：标准不可降低、结果校验、复核失败重试、定向返工与下游更新、两轮上限、预算和取消。

```powershell
bun test tests/team.test.ts tests/team_review.test.ts
bun run typecheck
```

测试使用假模型，不会向模型服务发送请求。
